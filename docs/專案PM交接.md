## 2. 和使用者相處

- **所有回覆一律用繁體中文**，精簡、有結論；比較選項用表格，並給出你的建議。使用者不是工程師，避免術語，必要時用遊戲例子解釋。
- 使用者習慣：先討論、比較，選定後說「好 寫入」才寫進設計文件；重大變更先問。**下載任何外部檔案前要使用者明確同意。**
- 使用者常自己開 `uv run trpg serve` 試玩（http://127.0.0.1:8000/）；前端改動後要請他 **重開伺服器** 才看得到。
- 底下 PM 的回報很長，轉述給使用者時濃縮成一兩句話，重點是「做完了什麼、要不要他決定什麼」。

## 3. 怎麼和底下的 PM 合作

### 3.1 上任後先建立底下的 PM 對話

使用者的安排：新的專案 PM 上任後，**先開新的玩法、開發、美術 PM 對話**（舊對話太長，已交接）。用 `start_session` 開，每個的 prompt 寫：

> 你是 ○○ PM。先讀 `docs/○○PM交接.md` 接手（只讀這份就能開始），需要時再讀 `CLAUDE.md`、`docs/專案計畫.md`。和使用者溝通一律用繁體中文。專案 PM 是 `<你的 session id>`，有結論或需要使用者決定的事，用 SendMessage 回報專案 PM，或直接問使用者。

- 開發 PM 與玩法 PM：`use_worktree: false`（在主資料夾工作）。美術 PM：`use_worktree: true`（在自己的分支做樣張）。
- 開完後，把各 PM 的 session id 記在本檔第 6 節。

### 3.2 傳話規則

- **PM 的 context 只放決策，不放細節（使用者 2026-10-22 指示，影響最大的一條）。** 手下（各 PM、實作與審查 agent）回報時只回結論和摘要：做了什麼、結果、卡在哪、要誰決定什麼。完整 log、測試輸出、程式碼、diff 留在手下自己的 context 或檔案裡，回報只附檔案位置與 commit。專案 PM 也不主動去讀細節，需要時請負責的 PM 查。每一層往上回報都照這個原則。
- 用 `SendMessage`，收件者用對方的 `local_…` session id。
- **使用者的決定要附原話**（「使用者原話：『……』」），不要只轉述你的理解；理解有疑義時先問使用者。
- 附上檔案位置與 commit，讓對方 `git pull` 後能找到。
- 一個 PM 的回報如果需要另一個 PM 處理（例如美術 PM 的需求要開發 PM 排段），由你轉達，或請它們直接互傳並副知你。
- 底下 PM 的回報是它們的說法，不是證據：重要的結果（例如「已完成」）可以用 `git log` 或對方給的截圖確認。

### 3.2.1 省額度的做法（2026-11-12，使用者原話：「4個都改」）

背景：第五組全部用 Fable 5.2，重設後約 5 小時用掉週額度 53%；主要花在長的 PM 對話每次被叫醒都要重讀、來回傳話、agent 開工前讀專案、樣張重畫與審查。

1. PM 不回報「還在跑、沒進展」，只在交件、合併／push、卡住、需要決定時回報。
2. agent 名額固定：開發 3、美術 1，不逐次互相確認；要借用才傳訊息。
3. PM 對話累積到約 40 萬 token 就在段落點寫交接、告知專案 PM「可以換手」，由專案 PM 開新對話（用 `get_usage` 看各對話大小）。**換手注意**：舊 PM 派出、還沒交件的 agent，完成通知只會回到舊 PM，舊 PM 會照習慣合併（2026-11-12 第六任開發 PM 交接後仍合併了 QI-2b，和第七任撞在 main 上）。換手時立刻傳訊給舊 PM：「已交接，之後收到任何通知都不要動 git、不派工，只回『請找新任』」，並在新 PM 的開場 prompt 寫明那些 agent 的分支。
4. 樣張與截圖審查只看有改動的圖；共用畫法檔有改時多抽 3～5 張未改的。

減少 agent 重讀專案（同日，使用者原話：「都做」；並強調不要改成 PM 自己做：「我怕 讓pm自己做 他會因為context window 一堆越做越笨」）：

- A. 同一塊的後續工作交回原本的 agent（SendMessage 接續），上限 2～3 段或約 30 萬 token。
- B. 每個區域一份上手筆記（`docs/dev/上手-<區域>.md`、`docs/art/上手-畫法.md`，150～300 行），交件時順手更新；開發的四份由換手後的新開發 PM 派 agent 寫。
- C. 派工 prompt 寫明要讀的檔與段落。
- D. 只有動同一批檔案的小修才併給一個 agent。

裝備有兩個關鍵字時（2026-11-12，⑤b）：使用者選 C「只畫一個圓章，旁邊加小記號表示還有一個」，原話「C」；記號再從 A「＋」版與 B 點版中選 B，原話「B」（「＋」會被讀成鐵匠的強化等級）。CB-4 硫煙獸斜向星爆超規格約 2 px，使用者原話「可以 push」，美術判維持。被前排遮住時畫剪影外框：使用者原話「做，現在排」；後因一般單位互擋時外框像配件，改成只在前排是大型單位時才畫，使用者原話「可以」。Mac 測試角色「測試」：使用者原話「刪」，下次在 Mac 上執行。使用者看過剪影外框樣張後原話「照建議刪，外框照做，C 先出設計」：舊 worktree 照建議刪（乾淨的刪、有未 commit 改動與可疑孤兒資料夾列出來再問）、剪影外框交開發、部位破壞 C 案（頭目仍佔 1 格）由玩法 PM 先出提案；多格頭目（B）等試玩 C 後再議。之後使用者提「不能移動的大型頭目」，原話「霧鎖真人 碎晶之主 這種偏人形小隻的擋的就少一點 就不要  然後像灰燼之心這種就很適合 但之後像那種3*3的龍可能還是要動?還是?」：人形頭目維持 1 格；灰燼之心改不動的多格頭目，玩法 PM 出提案（含會動的大型頭目選項）。續問後使用者原話「要，龍用 B」：人形頭目做部位破壞（選部位）、之後的大型會動頭目（龍）用定點飛行（落點間跳躍、不尋路）。合併提案 `docs/design/提案-頭目部位與巨型頭目.md` 6 項使用者原話「都照建議，好 寫入」：霧鎖真人先、灰燼之心 3×3 靠北、部位傷害算進 HP 且範圍技只打本體、殼縫算從背後、龍落點有人推開受傷、龍無空中狀態加翅膀部位；玩法 PM 寫入設計後交開發排段（#152）。PB-1 規格的 R1～R9 規則細節使用者原話「照建議」。之後一次答覆 5 件，原話「要改數值的都給我改就好 其他都按照建議」：部位選單 800 寬放上方、部位與 ⑦HUD 樣張無意見；技能比值目標只當報表參考線、數值工坊 NW-2（技能欄位）排最前、雙匕首另開玩法題、補量法器法術；碎晶之主採 B（被定身不能閃擊），A／C 數值交使用者；63 個 worktree 刪、孤兒資料夾先給美術看。BAL-21b 熔岩濺落測試放寬：使用者原話「C」（只列這一招為例外）。
