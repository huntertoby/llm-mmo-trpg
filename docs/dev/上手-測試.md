## 一、一律經看門狗跑 pytest

**不要直接 `uv run pytest`**，改用：

```bash
uv run python scripts/run_pytest.py -q tests/api/test_world.py -x            # 單檔
uv run python scripts/run_pytest.py -q tests/engine -n 8                      # 一個目錄，平行 8
uv run python scripts/run_pytest.py --stall-minutes 5 -q tests/world -n 8    # 改卡住門檻
```

**交件前**（CLAUDE.md 第 11 條；2026-11-21 使用者：「拿掉第二次重複的測試」）：

1. **全部 commit 之後**，在自己的 worktree 跑一次完整檢查：ruff、mypy、lint-imports，加上全部非 slow 的 pytest（經看門狗）。不加參數時會依改動分流（見一之一節）；分流跑寫的戳記 hook 不認（見一之二節）。
2. 再跑規格指定的 slow 測試。
3. 平行的 agent 交件前要錯開，由開發 PM 排順序，同一時間只跑一份全部測試。

```bash
uv run python scripts/check.py
```

全部通過、而且追蹤的檔案都已 commit 時，`check.py` 會依 HEAD 的 tree 寫一個通過戳記（見一之二節）。全跑通過的戳記，PM 合併後 tree 沒變，push hook 就略過完整檢查，只跑前端建置。所以**跑完之後不要再改檔**；有改就重新 commit，再重跑一次。

- 看門狗自己的選項放**最前面**（`--stall-minutes`、`--retries`、`--log-dir`、`--keep-logs`）；第一個不認得的參數起全部原樣交給 pytest（也可以用 `--` 分隔）。
- 結束碼：pytest 的結束碼原樣傳回；**124＝連續卡住判失敗**；130＝被中斷（Ctrl+C）或父程序消失。
- 完整檢查 `uv run python scripts/check.py` 的 pytest 步驟已經走看門狗，不用另外包。

## 一之一、check.py 依改動路徑分流（TS-1）

不加參數時，`check.py` 先看這次改了哪些檔，只跑會受影響的步驟。一開頭會印一行 `分流：…`，寫明跑哪些、略過哪些、為什麼。

**改動範圍**＝`origin/main` 和 HEAD 的 merge-base，到工作區為止的所有改動：已 commit 的、還沒 commit 的、未追蹤的都算。改名時新舊路徑都算。環境變數 `TRPG_CHECK_BASE` 可以換基準，例如驗收時用 `HEAD`。

| 改動 | 跑什麼 |
|---|---|
| 只動 `client/` | 前端的 install、typecheck、test、build，加上「讀 `client/` 檔案的 pytest」：測試檔裡有 `"client"` 或 `"client/…"` 字串，或用到有這種字串的輔助模組或腳本，現在約 18 檔。略過 ruff、mypy、lint-imports、其他 pytest、情境覆蓋表。 |
| 只動 `src/`、`tests/`、`scripts/` | 後端全部：ruff、format、mypy、lint-imports、pytest、情境覆蓋表。略過前端的 install、typecheck、test。 |
| 動到 `content/`、`config/`、`pyproject.toml`、`uv.lock`、`.python-version`、任何 `package.json` 或 lockfile、API schema（`client/openapi.json`、`client/src/api/schema.d.ts`）、`scripts/check.py` | 全跑 |
| 前端和後端都有動 | 全跑 |
| 動到其他位置，例如 `docs/` 的圖檔、`.claude/`、`.github/`、根目錄的設定檔 | 全跑。判斷不出來就全跑。 |
| 只有 `.md` 或沒有改動 | 全跑。`.md` 本身不影響分流；跟程式一起改時照程式那一邊算。 |
| 沒有 `origin/main`、git 失敗 | 全跑 |

- **API schema 怎麼判斷**：後端改了 API 卻沒重產 `client/openapi.json` 時，`tests/api/test_openapi_snapshot.py` 會失敗，只跑後端也一樣擋得下來。重產後 `openapi.json` 或 `schema.d.ts` 會變，就落到「全跑」。
- **強制全跑**：`uv run python scripts/check.py --all` 不分流，等於 TS-1 以前不加參數的行為。`--full` 照舊全跑，還會加上 slow 測試。
- push hook 跑的也是不加參數的 `check.py`，所以 hook 也會分流，基準就是 `origin/main`，也就是這次要推的 commit 加上工作區的改動。

## 一之二、通過戳記的意思

戳記放在 `<git common dir>` 底下，檔名是 HEAD 的 tree hash。內容三行：commit、`scope:` 範圍、`base:` 比對基準。

| 戳記位置 | 什麼時候寫 | hook 看不看 |
|---|---|---|
| `pm-check-pass/<tree>` | 全部步驟都跑了（範圍 `all`，包含 `--all`、`--full`）並且通過 | 看。同內容 push 時略過完整檢查。 |
| `pm-check-pass-split/<tree>` | 分流跑：有步驟被略過，其餘都通過 | 不看。只是紀錄，push 時 hook 照常跑，hook 自己也會分流。 |

分流戳記不放進 hook 看的位置，原因是 hook 只認 tree：同一份內容換一個基準，該跑的範圍可能不同，hook 分辨不出來。要讓 hook 略過，那一次就要全跑，例如加 `--all`。交件前要分流跑還是全跑，等 PM 定案（見 `docs/phases/PhaseTS-1報告.md`）。

## 二、看門狗怎麼判卡住

- **進展**＝任何一個測試跑完。還沒有測試開始時（收集階段）看 pytest 有沒有輸出。
- 超過 **10 分鐘**（`--stall-minutes`，或環境變數 `TRPG_PYTEST_STALL_MINUTES`）沒有進展就算卡住。正在跑的測試如果自己的逾時比門檻長（標 slow 的 1800 秒），等到它的逾時＋60 秒才算。
- 卡住時：用 **PID** 結束自己開的 pytest 和底下所有 worker（Windows `taskkill /T /F /PID`，其他系統結束自己開的 process group），**不用程序名稱**；寫 `stuck.txt`、自動重跑一次（`--retries`）；再卡住就判失敗（124）。
- 單一測試的逾時（`pyproject.toml` 的 `timeout = 300`，slow 1800）照舊由 pytest-timeout 管；看門狗管的是整組不再前進。

## 三、留證在哪裡

`.claude/pm-logs/pytest/<時間>-<pid>/attempt-<N>/`（已在 `.gitignore`）：

| 檔案 | 內容 |
|---|---|
| `output.log` | pytest 的完整輸出 |
| `trace/<worker>-<pid>.trace` | 每個測試的 `START`／`END` 行（`tests/pytest_trace.py` 寫）；只有 START 沒有 END 的就是那個行程最後在跑的測試 |
| `trace/<worker>-<pid>.stacks` | `faulthandler` 輸出：行程致命錯誤時的 stack，以及測試快逾時（逾時前 5 秒）時所有執行緒的 stack |
| `stuck.txt` | 卡住時的摘要：每個行程最後沒結束的測試、已跑秒數、非空的 stack 檔 |

- 全部通過、沒有 worker 掛掉時，整個資料夾自動刪掉（`--keep-logs` 保留）。有失敗、有 worker 掛掉（輸出有 `node down`）、有 stack、或卡住時保留，並印出路徑。
- 回報 worker 掛掉時，附上保留下來的資料夾路徑和 `stuck.txt`／`.stacks` 的內容。

## 四、xdist 的坑

1. **`--dist loadgroup` 在 worker 掛掉後會卡死**（xdist 3.8 的排程問題，QF-3a 查到）：補上的新 worker 只拿到一個測試，等不到「下一個測試」所以永遠不開始。`tests/xdist_loadgroup.py` 已修（`tests/conftest.py` 匯入），掛掉時那個測試回報失敗、不重跑。詳見 `docs/phases/PhaseQF-3a報告.md`。
2. worker 掛掉的訊息是 `[gwN] node down: Not properly terminated`，緊接著 `worker 'gwN' crashed while running '<測試>'`。最常見的原因是測試超過 pytest-timeout 的逾時（thread 方式會 `os._exit` 整個 worker）；那個測試的 stack 在 `.stacks`。
3. **不要用程序名稱殺 python**（會誤殺別的 agent 的 worker）；要停自己的測試，停自己開的那個指令，看門狗會收整棵樹。

## 五、示範與驗證（不進推送前檢查）

`tests/infra/stuck_suite/` 的三個檔名不符合 `test_*.py`，而且沒設 `TRPG_WATCHDOG_DEMO=1` 時整檔跳過：

```bash
TRPG_WATCHDOG_DEMO=1 uv run python scripts/run_pytest.py --stall-minutes 0.5 tests/infra/stuck_suite/hang_case.py -n 2 -p no:cacheprovider -v
```

預期約 1 分半後結束碼 124，兩次 `stuck.txt` 都寫 `test_hangs_forever`。`crash_case.py`、`timeout_case.py` 由 `tests/infra/test_xdist_loadgroup.py` 複製到暫存資料夾跑。

`test_xdist_loadgroup.py` 的時限：worker 掛掉的兩題（`crash_case.py`、`crash_twice_case.py`）是 540 秒，`timeout_case.py` 是 240 秒。逾時時，失敗訊息會附上子程序主行程（xdist master）在時限前 20 秒寫的所有執行緒 stack（`master-hang.stacks`）；如果子測試都已回報 `[100%]`，訊息會註明「卡在主行程收尾」。2026-11-21、11-22 兩次逾時都是這種情形，原因還沒查到（TS-1 報告）。
