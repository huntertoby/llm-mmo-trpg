# 現代網頁指南試用（modern-web-guidance）

> 2026-11-13，研究報告，沒有改程式。使用者核可試用一次（原話「試用」，專案 PM 轉達）。
> 工具：`github.com/GoogleChrome/modern-web-guidance`（Apache-2.0，Chrome、Edge、Firefox、MDN 團隊維護），用 `npx modern-web-guidance@latest` 執行，沒有 install、沒有裝成 plugin、沒有改任何設定。
> 範圍：`client/` 的 DOM／CSS 那一半。PixiJS 畫布不在這份指南的範圍內。

## 一、跑了什麼、工具看到什麼

| 指令 | 結果 |
|---|---|
| `legacy-scan client/` | **2 條**，同一份指南 `ime-safe-enter-submit`（見第二節 A）。工具自己說：只用確定性規則掃了 33 份指南，約佔全部指南的 20%；跳過 343 個文件與測試檔 |
| `legacy-scan client/ --include-docs-and-tests` | 同樣 2 條（開發頁、測試檔沒有多找到） |
| `retrieve`（手動查） | `improve-text-layout-and-legibility`、`equal-width-text-lines`、`position-aware-tooltips`、`viewport-aware-dropdowns`、`hovercard`、`interest-triggered-tooltips`、`persistent-top-layer-ui`、`size-aware-styling`、`soft-edge-content-fade`、`scrollability-affordance-hints`、`scroll-position-aware-elements`、`state-aware-sticky-headers` |

**自動掃描能抓的很少**：它只認得「舊寫法 → 新寫法」的固定樣式。我們踩過的坑大多是版面與互動設計，要靠人手對照指南（第三節）。

**工具的相容性資料要再核對一次**：三份指南對 anchor positioning 都寫「只有 Safari 27（2026-09）支援，Chrome、Edge、Firefox 不支援」。這和已知情況矛盾：Chrome、Edge 從 125 版（2024-05）起就有基本的 anchor positioning。推測是 web-features 把較新的子功能也算進「整組」，所以整組標成未支援。之後真的要用 anchor positioning 時，要先用 caniuse／MDN 逐個屬性查過。其他特性的版本號和我們已知的一致。

**我們要支援哪些瀏覽器**：文件裡沒有寫明的目標。可以參考的先例：6F-ART1b 檢查接受「舊 Safari 不支援 `ctx.filter`，未開放的島變成彩色」（`docs/archive/art/6F-ART1b檢查.md` 第 3 條），可見目前的實際做法是：**主力是新版 Chrome、Edge；Firefox、Safari 要能玩，外觀可以降級**。下面的「需不需要」都照這個標準判斷；如果之後要把這條寫成正式規定，要由使用者決定。

## 二、值得改的地方

### A. 中文輸入法按 Enter 選字時，會把半截字送出（**建議做，最優先**）

| 項目 | 內容 |
|---|---|
| 在哪 | `client/src/world/NotesPanel.tsx:121`（留言輸入框：`if (e.key === "Enter") void send();`）、`client/src/world/MailPanel.tsx:111`（郵寄個數框：`if (e.key === "Enter") commit();`） |
| 問題 | 用注音、倉頡、拼音輸入法時，Enter 是用來「確定選字」的。這兩個 `keydown` 沒有檢查 `e.nativeEvent.isComposing`，所以玩家選字那一下就會把還在組字的半截留言送出去。留言是給其他玩家看的，送出後收不回來。郵寄個數框一般只打數字，影響小，但日文輸入法打數字時也會組字，所以一併處理 |
| 改法 | 判斷 Enter 之後，先檢查 `e.nativeEvent.isComposing \|\| e.keyCode === 229`，是的話就直接 return。指南的寫法是同時檢查這兩個條件（Strategy 1）。寫成共用小函式（例如 `isImeEnter(e)`），再加一條原始碼掃描測試：所有文字輸入框的 Enter 處理都要經過這個函式（做法同 `floatCardRule.test.ts`） |
| 效益 | 修好一個真的會發生的 bug。玩家主要用繁體中文，每個人都會碰到 |
| 風險 | 很低。改動只有幾行，不影響英數輸入 |
| 相容性 | `isComposing`：Chrome 56、Edge 79、Firefox 31 起支援，**Safari 不支援**，而且舊版 Safari 會先送 `compositionend` 才送 `keydown`。加上 `keyCode === 229` 就能涵蓋 Safari（組字中按 Enter，`keyCode` 是 229）。**Firefox、Safari 都需要支援**：用 macOS 的玩家常用 Safari，而且這個問題不是外觀，是功能 |
| 已確認沒問題的其他 Enter | `RangeClassPick.tsx:54`、`RunFlashPending.tsx:216`、`PartTip.tsx:32`、`PartMenu.tsx:153` 都掛在卡片或選單上，不是文字輸入框，不會碰到輸入法，不用改 |

### B. 浮動卡被捲動區切掉：Popover API＋anchor positioning（**不建議現在換**）

現況：說明卡（`useFloatCard.tsx`、`HoverFloat.tsx`）用 `createPortal` 放在 `document.body`，`position: fixed`，位置由 `floatCard.ts` 的 `floatPlacement`／`sidePlacement` 計算。`floatCardRule.test.ts` 只允許共用元件和 `PopupSlot.tsx` 使用 portal。`PopupSlot` 把標頭和確定列放進框的上下固定區，它本身不是彈出層。

| 能取代什麼 | 評估 |
|---|---|
| **Popover API**（`popover` 屬性，元素放進 top layer） | 能取代 portal：top layer 不會被祖先的 `overflow`、`transform`、`z-index` 擋住，所以元件可以留在原本的 React 樹裡。相容性：Chrome 116、Edge 116、Firefox 125、Safari 17 起支援，**Baseline 2025-01**，四家都可以用 |
| **Anchor positioning**（`position-anchor`、`position-area`、`position-try-fallbacks: flip-block`） | 能取代「貼齊觸發元素、上方放不下就翻到下方」這一段計算。但我們的規則還有幾條它做不到：透明橋接區 `BRIDGE_PX`、`HoverFloat` 要夾進戰場區的可見範圍（不只是夾在視窗內）、PB-1c 的「上方放不下就退回左右、不翻到下方」、`anchorOutOfView`。這幾條仍然要用 JS。相容性見第一節：工具資料寫 Chrome、Edge 不支援，和已知情況不一致；Firefox 是近期才開始支援。我們的需求是 Firefox、Safari 也要正常顯示說明卡（說明卡是功能，不是裝飾），所以還得加 `@oddbird/css-anchor-positioning` polyfill。這個 polyfill 不支援隱含錨點，也不支援 `position-area` 搭配 fallback |
| **`popover="hint"`、`interestfor`**（滑過開說明） | 可以取代 `OPEN_DELAY_MS`、`CLOSE_GRACE_MS` 的計時器。但 `interestfor` 只有 Chrome、Edge 149 起支援，`hint` 在 Safari 不支援。我們還有 `pinOn: "hold"` 長按、釘住等規則，標準做不到，**不適用** |

- **效益**：可以少用一個 portal。如果全面改用 anchor positioning，可以少掉一部分位置計算，但其他規則仍然要留在 JS。
- **風險**：高。`floatCardLayout.test.ts` 用改前的函式逐格比對，鎖住了現在的位置；換掉之後每種說明卡都要重新驗位置，美術驗收也要重來。HUD 外層有縮放 `transform`，卡片放進 top layer 之後就不會跟著縮放，大小會和現在不一樣。
- **結論**：現在的 portal 做法沒有壞，換掉主要只是讓寫法更新。**不排**。可以留一個小改進：之後如果碰到「說明卡被對話框（`DialogFrame`）蓋住」這類疊層問題，可以只在外層加 `popover="manual"`，用 top layer 解決，位置計算照舊。

### C. 800 與 1600 兩種排法：container queries（**已經在用，只建議小修**）

結論：**已經改成看面板寬，不看視窗寬了**。目前用到的地方：

- `world-hud.css:978` `.world-hud-panel { container: world-panel / inline-size }`，配 `@container world-panel (max-width: 559px)`（`world-hud.css`、`world-panel-board.css`、`world-panel-quest.css`）。
- `flash-choice.css:37` `.fc-run { container-type: inline-size }`，配 `@container (max-width: 559px)`（`flash-choice.css:625`）。
- `world/mail.css:66`，配 `@container (width < 560px)`。

相容性：Chrome、Edge 105，Firefox 110，Safari 16，**Baseline 2023-02**，四家都支援，不用另做退路。

可以小修的地方：

1. **沒有命名的容器查詢**：`flash-choice.css:625`、`world/mail.css:95,492`。沒有命名的 `@container` 會對到最近的容器祖先。以後如果中間多包一層 `container-type`（例如把面板放進另一個有容器查詢的分頁），窄版判斷會悄悄改成量那一層的寬度。改成命名容器（`container: fc / inline-size`，再寫 `@container fc (...)`）就能避免。**效益**：防止以後出錯。**風險**：幾乎沒有，但要讓 `pnl1bBoard.test.ts` 這類掃 CSS 字串的測試跟著改。
2. **戰鬥畫面的 `.battle-screen.narrow`**（`battle-layout.css:470-494`、`battle-hud.css:430`）：由 `useNarrow()` 的 `window.innerWidth < 1100` 加上 class。這些 CSS 規則可以改成 `@media (width < 1100px)`，但 `useBoardViewport` 等 JS 本來就要用 `narrow` 來算版面，所以 class 還是會留著，改了只是多一種寫法。**不建議改**。`PartMenu` 的 `< 1000`、`HUD_NARROW = 900` 也都是 JS 計算要用的值，同樣不適合改成 CSS。

### D. 彈窗與捲動區上下緣的漸隱（**可以做，但不急**）

現況（`styles/theme.css:136-185`，`PopupFrame.tsx`）：上下緣的漸隱是 sticky 的 `::before`、`::after` 色塊，顏色漸到 `--ui-navy`。JS 用 `ResizeObserver` 和捲動事件標 `data-scrolled`、`data-overflow`、`data-end`；CSS 依這三個標記開關漸隱，並在不需要時把高度收成 0。程式裡有 `BOTTOM_FADE_PX` 扣掉漸隱自己佔的高度，就是為了避免高度來回跳。

指南（`scrollability-affordance-hints`、`soft-edge-content-fade`）建議的寫法：

- **淡化內容本身**：在捲動區設 `mask`（一層不透明減掉上下兩條漸層），再用 `animation-timeline: scroll(self block)` 讓上下兩條漸層的高度跟著捲動位置變化。不捲時沒有漸隱，捲到底時下緣漸隱自動消失。內容放得下時捲動時間軸不會啟動，就不會有漸隱。**完全不佔版面，不需要 JS**，`data-overflow`、`data-end`、`BOTTOM_FADE_PX` 和「扣掉自己的高度」那些補丁都可以拿掉。
- 或者用 `container-type: scroll-state` 加 `@container scroll-state(scrollable: block-end)` 開關陰影。

| 項目 | 內容 |
|---|---|
| 效益 | 少掉 `useOverflowFlag`、三個 `data-*`、RT-3b 與 6F-8 的高度補丁（大約 40 行 TS 和 30 行 CSS）。底色換成不是實色的框（例如事件卡）時，也不用另外配一個漸層色 |
| 風險 | 中等。(1) 遮罩會連捲軸、焦點框、捲動區裡的 sticky 元素一起淡化，指南用「減掉兩條帶子」的寫法可以保住焦點框，但捲軸兩端還是會變淡。(2) 美術 PM 調過的精細漸層（上緣實色 70%、下緣後 55% 實色）要用遮罩重新做出來，**要重新做美術驗收**。(3) `theme.css` 有不少測試直接掃 CSS 字串，要跟著改 |
| 相容性 | 遮罩：**Baseline 2023-12**，四家都支援。Scroll-driven animations：Chrome、Edge 115，Safari 26（2025-09），Firefox 159（2026-10），**Baseline 2026-10-27，剛剛才四家都支援**；舊一點的 Firefox、Safari 會沒有漸隱，但內容照樣能捲。`scroll-state` 查詢只有 Chrome、Edge 144 支援，**不建議用** |
| 我們需不需要 Firefox、Safari 也有漸隱 | 不需要。漸隱是外觀，沒有它最多是看到切半的一行字，捲動功能不受影響。可以用 `@supports (animation-timeline: scroll())` 包住新寫法，不支援的瀏覽器繼續用現在的 JS 做法（舊程式要留著當退路，等於兩套並存，這是這條的主要成本） |
| 結論 | 現在的做法能用，也驗收過了。**等下次要動 `PopupFrame` 的漸隱時再一起換**，不要單獨排一段 |

### E. 中文標題在詞中間斷行（**現在的做法是對的，不用改**）

現況：
- FL-1b `.fc-headline`（`flash-choice.css:268`）、`story.css:227`、`atlas.css:55`：`word-break: keep-all; overflow-wrap: anywhere`，呼叫端在詞和詞之間插 `<wbr>`（`world/solutionGrid.ts` 的 `wordBreaks()`）。
- `base.css:132-145`：`.decision-card p`、`.mode-help .op-hint` 用 `text-wrap: balance`；`.op-hint`、`.part-tip-text`、`.skill-hint` 用 `text-wrap: pretty`。
- `index.html` 的 `<html lang="zh-Hant-TW">` 有設好，斷行規則和字型都會照中文處理。

對照指南：
- `text-wrap: balance`：Chrome、Edge 114，Firefox 121，Safari 17.5，**Baseline 2024-05**。指南提醒 Chromium 只會平衡 6 行以內的文字，超過就照一般方式斷行；我們用在短段落，沒問題。
- `text-wrap: pretty`：Chrome、Edge 117，Safari 26 支援，**Firefox 不支援**，不支援時就照一般方式斷行。這是外觀，**不需要** Firefox 也支援。
- 指南沒有能自動找出中文詞界的 CSS。Chrome 的 `word-break: auto-phrase` 依我們所知目前只支援日文（`lang="ja"`），中文用不到；指南也沒有提到它。所以「`keep-all`＋自己插 `<wbr>`」仍然是唯一可靠的做法。
- 可以順手加的：`.fc-headline` 最多折兩行，可以加 `text-wrap: balance`，讓兩行長度接近，避免第二行只剩一兩個字。**效益**：小。**風險**：`balance` 和 `-webkit-line-clamp` 一起用時，截斷的位置可能會變，要截圖確認。Firefox 121 起支援。**列為可選**。

### F. 只靠顏色區分的記號（**已達標，不用改**）

FL-1b 的四種「後」樣式（`flash-choice.css:358`）：實心底、細框加警告三角、無底加向下三角、綠「新」。不靠顏色也分得開，符合指南 `accessibility` 的原則。沒有要改的地方。

### G. 其他順手看到的

- `:has()`（`world-hud.css`、`battle-hud.css`、`flash-choice.css` 等）是 Baseline 2023-12，四家都支援，沒問題。
- `.ui-popup-body` 已經有 `overscroll-behavior: contain`（指南 `prevent-page-scroll-under-modal-dialog` 的建議），沒問題。
- `line-clamp` 同時寫了 `-webkit-line-clamp` 和標準的 `line-clamp`，沒問題。

## 三、對照表（我們踩過的坑）

| 坑 | 現在的做法 | 指南的建議 | 結論 |
|---|---|---|---|
| 標題在詞中間斷行 | `keep-all`＋`overflow-wrap: anywhere`＋`<wbr>`；`text-wrap: pretty`／`balance` | 同樣是 `text-wrap`；沒有中文斷詞的 CSS | 不用改；`.fc-headline` 可選加 `balance` |
| 說明卡被捲動區切掉 | portal 放到 body＋`position: fixed`＋`floatPlacement` | Popover（top layer）＋anchor positioning | 不換；只有遇到疊層問題時才考慮 `popover="manual"` |
| 800／1600 兩種排法 | 已經用 container queries（面板 < 560） | 同樣是 container queries | 把沒有命名的 `@container` 改成命名（小修） |
| 彈窗上下緣漸隱 | sticky 色塊＋JS 標 `data-*` | mask＋scroll-driven animation | 可以做，等下次動到漸隱時再一起換 |
| 只靠顏色區分 | 框加三角加文字 | 不只靠顏色 | 已達標 |

## 四、結論

**值得排，但只值得排一小段（1 段）**。這個工具的主要價值是幫我們找到一個真的會發生的 bug（第二節 A）；其他幾個踩過的坑，我們現在的做法大多已經跟指南一致，或者比指南的標準做法更貼近我們的需求。

建議的順序：

1. **A 輸入法 Enter**（`NotesPanel.tsx`、`MailPanel.tsx`，加共用判斷和原始碼掃描測試）：一定要做，所有瀏覽器都要支援。
2. **C-1 容器查詢加上命名**（`flash-choice.css`、`world/mail.css`）：防止以後出錯，跟著測試字串一起改。
3. **E `.fc-headline` 加 `text-wrap: balance`**（可選）：要截圖確認，可以交給美術 PM 決定要不要。

這三條可以合成一段小修，不用另開一段，併進開發 PM 的下一段就好。D（漸隱改用 mask）等下次要動 `PopupFrame` 的漸隱時再一起做；B（Popover／anchor positioning）不排。

**工具本身值不值得留著用**：可以偶爾跑一次 `legacy-scan`。它跑得快、不用安裝，可以留在 PM 的大階段檢查清單上，但不要寫進 CI，因為它只用確定性規則掃了約 20% 的指南。相容性資料要再核對（anchor positioning 那筆就有問題）。這次沒有安裝它的 skill，也沒有改任何設定。
