- 範圍：`src/trpg/skillgen/proposal_witness.py`（新）、`src/trpg/skillgen/proposal_topic.py`（`make_topic` 套用）、`tests/skillgen/test_witness_6ew.py`（新）、`tests/skillgen/test_topup_6s2c.py`（fixture 沿用舊題目，見 5.3）。
- 驗證規則、預算數值與上下限、提示詞（`PROMPT_VERSION`）都沒有改。
- 12B：LM Studio `http://127.0.0.1:1234/v1`，`gemma-4-12b-it`，`reasoning_effort=none`，`max_retries=3`，一次一個請求。設定在 scratchpad 的暫存 toml，用 `TRPG_LLM_CONFIG` 指定；repo 的 `config/llm.toml` 沒改。沒有碰模型伺服器，只送請求（另外讀了一次 `GET /api/v0/models/gemma-4-12b-it`：`loaded_context_length = 8192`）。
- 暫存腳本與原始輸出在 `scratchpad/ew/`，沒進版控。

## 0. 結論

1. **「白板出題沒有套用 6S-2 過濾」這個判斷不成立。** 兩條路徑共用同一個 `make_topic`，6S-2 的 `keywords_reachable` 兩邊都有套到。問題在這個過濾只是「每個關鍵字各自檢查」的必要條件。實戰題目常有兩個關鍵字、指定武器大類，組合起來就會不可能（見第 1 節）。
2. **實戰題目中，靜態上找不到合法解的約有 37%**（265 題中 97 題，第 2 節）。評估集看不到這個問題，因為評估集的題目最多一個關鍵字，也不指定武器。
3. **12B 這次退回率 80.5% 的最大原因是伺服器，不是題目。** 改前 52% 的嘗試是 `llm.bad_response`，LM Studio 回的是 HTTP 400「Context size has been exceeded」（載入的 context 是 8192）。同一時段跑評估集 50 題，退回率也是 48%（記錄值是 32%）。
4. **修正**：`make_topic` 加了一道「可行解檢查」。引擎自己建構最簡單的寫法，用和 LLM 提議完全相同的 `evaluate_with_repair` 驗證，至少一份通過才出題。改後同一批種子的結果：
   - 退回率 80.5% → **47.2%**；
   - 平均嘗試次數 2.69 → 2.37；
   - 每張白板拿到的 LLM 卡從 0.46 張增加到 **1.17 張**。
5. **每張白板的等待秒數反而變長**：28.6 → 49.1 秒，詳見 4.2。主要原因有三個：
   - 過的題目變多，命名呼叫跟著變多；
   - 原本會很快失敗的 context 爆量嘗試變少了；
   - 這段時間伺服器每次呼叫的延遲變高，從 3.7 秒升到 5.4 秒，還遇到一次 120 秒逾時。
   以每張白板的 LLM 呼叫次數來比，前後差不多（7.25 → 7.29 次）。另外，出題檢查每張白板要多花 **平均 4.3 秒 CPU**（列入待決）。
6. **大世界沒有動到**：大世界不會呼叫 `make_topic`（第 5.2 節），結果不變，不需要升 `WORLD_RULES_VERSION`。存檔格式也沒有升版。

## 1. 兩條出題路徑

| | 評估集「升級候選」（`skill_eval.upgrade_items`） | roguelite 實戰（`trpg run auto --llm`） |
|---|---|---|
| 進入點 | `_upgrade_topic` → `make_topic` | 完整技能三選一 `offers._compute_offer`（`complete=True`）→ `generate_candidates` → `_Search.from_llm` → `make_topic` |
| 升級（level_up）白板 | — | `generate_whiteboard_candidates`，**不呼叫 LLM**（白板模式下 LLM 來源關閉）。所以 12B 報告裡的「白板候選」其實是完整技能三選一 |
| 關鍵字 | 0 或 1 個（一半帶） | 加深 1 個、**橋接 2 個**、新方向 1 個；實際抽到 37% 是 2 個 |
| 武器大類 `weapon_class` | 不指定 | 指定（近戰、遠程、法器），驗證時會檢查 `weapon.incompatible` |
| 主角屬性、手上武器 | 不給 | 給（`hero_attributes`、`held`） |
| 核心原語 | `make_topic` 依配額抽 | 同一個函式 |
| 稀有度、反應技 | `make_topic` 依權重 | 同一個函式（`llm_reaction_permille` 100‰） |
| 6S-2 過濾（`keywords_reachable`） | **有** | **有**（同一段程式） |

6S-2 的過濾逐個關鍵字檢查：原語在選單裡、放得進某個骨架、狀態稀有度夠。以下幾種情況它看不到：

- 兩個關鍵字各要一個附帶效果，但骨架的附帶效果只能 1 個；
- 角色 1 階不能帶兩種傷害元素（`tier.element`）；
- 地形核心限大地元素（`terrain_needs_earth`），影響格數也受角色階級限制；
- 沒有數值的核心放在附帶效果有占比上限的骨架上，例如控場骨架的傷害 ≤ 40%，總強度補不到預算下限；
- 骨架不允許的對象（光環不得對敵、核心狀態必須有益）；
- 技能和主角武器不相容。

## 2. 靜態不可能的比例（不呼叫 LLM）

**抽題方式**：走實際的 `generate_candidates` 路徑。

- 開局用 8 組設定：`fire_staff` 點燃＋帶電（魔族）、`dagger` 冰凍＋隱蔽（精靈）、`greatsword` 倒地＋撞擊、`bow` 標記＋高處、`frost_staff` 冰凍＋潮濕、`hammer` 撞擊＋點燃、`totem_staff` 召喚物＋中毒、`spear` 帶電＋標記。出身都是 `origin_cloud_ridge`。
- 每組都取 `candidate_request` 的真實輸入，再搭配角色階級 1～3、各 5 個種子，共 120 組三選一。
- 裝一個「記錄題目後回報失敗」的提議器，讓產生器照退回路徑走，和 12B 多數退回的情形相同。共抽到 **265 題**。

**判斷方式（建構式）**：對每題建構提議，交給 `evaluate_with_repair` 完整驗證（含數值修補、結構補強、題目要求、武器相容）。任何一份合格就算可行。

- 建構方式：骨架 × 形狀 × 對象 × 相容的類別 × 技能元素，從「核心效果＋每個關鍵字一個專屬效果」出發。
- 用了兩套建構器：scratch 版最多試 1500 份；產品版就是 5.1 的檢查，最多試 400 份。兩套結果取聯集。

| | 題數 | 占比 |
|---|---:|---:|
| 找得到合法寫法 | 168 | 63.4% |
| **找不到合法寫法** | **97** | **36.6%** |
| 　其中 2 個關鍵字的題 | 54／99 | 54.5% |
| 　其中 1 個關鍵字的題 | 43／166 | 25.9% |

找不到的 97 題分類（依剩下最多的錯誤代碼）：

| 類別 | 題數 | 例子（核心／關鍵字） |
|---|---:|---|
| 補不到預算下限（沒有數值的核心，附帶效果有占比上限） | 18 | 驅散／撞擊、拉扯／高處、淨地／倒地 |
| 地形限大地元素、格數受階級限制 | 11 | 下陷地形／標記（1 階）、隆起地形／倒地＋撞擊 |
| 兩個關鍵字，但附帶效果只能 1 個 | 10 | 回復資源／冰凍＋隱蔽、賦予技能／倒地＋撞擊 |
| 選單裡帶不到關鍵字 | 9 | 衝鋒穿越／點燃＋帶電、揭露／倒地 |
| 1 階帶兩種傷害元素 | 6 | 傷害／冰凍＋隱蔽（普通）、揭露／點燃＋帶電 |

**誤差說明**：這是「建構器找不到」，不是數學證明。12B 在改前被判為不可行的 49 題裡過了 7 題（14%），所以 36.6% 是上限，實際的靜態不可能比例約在 30% 上下。「其他」這一類最可能包含建構器漏抓的題目。

12B 報告裡的三個例子對照：

- 「治療＋冰凍」：屬於骨架對象問題，光環不得對敵，冰凍又只能打敵方。
- 「下陷地形＋冰凍」：地形限大地，1 階加冰霜就是兩種元素。
- 「製造地表＋撞擊」：骨架不允許。

這三類都在上表裡。

## 4. 修了什麼

### 4.1 `proposal_witness.has_witness`（新模組，純函式、確定性）

針對每個題目，引擎依序建構提議：

- 骨架：選單裡的每個骨架輪流出一份；
- 核心效果：先試帶到題目關鍵字的寫法，再試手寫技能的寫法（只留選單可用的列舉值），最後試必填列舉欄位的可用值；
- 關鍵字效果：每個題目關鍵字一個專屬效果；
- 其他組合：對象、和武器相容的類別、互斥規則要求的技能元素（地形 → 大地）、前 4 個形狀，反應技再加觸發事件。

每份提議都交給 `evaluate_with_repair`，和 LLM 提議走同一個函式，包含數值修補、結構補強、`validate_skill`、題目的關鍵字、核心與武器相容檢查。第一份合格就判定「可行」。

- 上限 `WITNESS_MAX = 48` 份（原型值）。
- 驗證全部照舊，沒有放寬；這道檢查只決定要不要出這個題目。
- 順序只依內容庫與題目決定（排序、JSON 鍵），不用亂數、不用內建 `hash()`。

### 4.2 `make_topic` 的套用

- 指定核心時：原本要求 `keywords_reachable`，現在還要 `has_witness`。不過就換下一個核心，最多重抽 `CORE_RETRIES = 4` 次，這部分和 6S-2 相同。
- 都不行時改成不指定核心：這種題目也要通過 `has_witness`，否則換下一個稀有度。所有稀有度都不行就回傳 `None`，這一格不請 LLM。
- 檢查用固定種子 `WITNESS_SEED = 0`，**不消耗出題的亂數串流**。第一次抽到的題目如果通過檢查，結果和改前一字不差（測試 `test_passing_topics_are_unchanged`）。這次 265 題中，依位置比對有 134 題沒變。

### 4.3 等待時間為什麼變長

- **命名呼叫**：LLM 卡從 0.46 張增加到 1.17 張，命名呼叫也從 0.92 次增加到 2.06 次。
- **context 爆量的嘗試**：改前大多不到 1 秒就失敗，改後這類嘗試變少，變成真正的生成，每次 4～8 秒。
- **伺服器延遲**：改後那段時間延遲變高（中位數 3.7 → 5.4 秒），還有一題遇到 120 秒逾時，單題就花了 339 秒。這台 LM Studio 是共用的。
- **換算成同樣的延遲**：每張白板的 LLM 呼叫次數前後差不多（7.25 → 7.29 次），但改後多拿了 1.5 倍的 LLM 卡。以「每張 LLM 卡的等待」來看，從 62 秒降到 42 秒。
- **出題 CPU**：每張白板多 4.3 秒，這是新增的成本（見待決 2）。

## 5. 影響範圍與版本

### 5.1 會受影響的地方（凡是呼叫 `make_topic` 的）

- roguelite 完整技能三選一的 LLM 來源（CLI `--llm`／`--llm-mock`、API 的瀏覽器 roguelite）。只有 `run.llm` 為真時才會呼叫 `make_topic`；**沒開 LLM 的 run 結果完全不變**。
- 評估集的升級候選、自由測試出題（`skill_eval.upgrade_items`、`free_items`）。題目會換掉部分不可行的題，之後的評估數字和 6S-2c 之前的不能直接比。強制測試不經過 `make_topic`，不受影響。

### 5.2 大世界

- 大世界的白板與三選一走 `make_offer`，用的是大世界自己的 `RunState`。
- 大世界程式裡沒有任何地方把 `run.llm` 設成真（`src/trpg/world` 搜尋不到），所以 `from_llm` 在 `make_topic` 之前就回傳了。
- **大世界白板的結果不變**，不需要升 `WORLD_RULES_VERSION`。

### 5.3 重播與存檔

- roguelite 的三選一（候選技能＋`OfferTag`／`LlmRecord` 題目紀錄）存在 `RunState` 裡。重播和讀檔直接用存下來的候選，不會重新出題、也不會呼叫 LLM。
- 所以舊 run 不受影響，**`SAVE_FORMAT` 不升版**。
- 新開的 `--llm`／`--llm-mock` run，同樣的種子可能出不同的題，這是這段的直接效果。
- 提示詞沒改，`PROMPT_VERSION` 不變。
- 戰鬥重播：`trpg battle --map swamp --seed 7` 存檔後跑 `battle replay`，驗證通過（88 個動作、313 個事件）。

### 5.4 測試

- `tests/skillgen/test_witness_6ew.py`（新，11 個）：
  - 3 個從實戰路徑抽出、靜態不可行的原題判為不可行；
  - 可行題找到的寫法真的通過完整驗證、用到指定核心；
  - 建構順序具確定性；
  - 4 組橋接（兩個關鍵字＋武器大類）× 種子 × 階級，`make_topic` 出的題都通過檢查，而且同輸入同結果；
  - 通過檢查的題和不檢查時相同。
- `test_topup_6s2c.py::test_upgrade_topup_distribution`：這組表格驗的是補強的附帶效果順序，樣本取自 `upgrade_items(seed=0)`。6E-W 換掉部分題目後，樣本變成全是治療，斷言失敗。改成在 fixture 裡關掉可行解檢查，沿用 6S-2c 的同一批題目。斷言本身沒有改。
- 檢查結果：
  - `ruff check`、`ruff format --check`、`mypy src`（514 檔）、`lint-imports`（13 條契約）都通過。
  - `pytest tests/skillgen tests/llm tests/roguelite -n 6`：4384 通過、14 略過。另有 2 個失敗：`test_proposal_l8b_topic.py` 的兩個測試在平行時出現 `MemoryError`。當時機器上同時有 LM Studio 和我的 12B 評估在跑，單獨重跑這個檔案 7 個全部通過。

## 6. 待 PM 決定

1. **LM Studio 的 context**：`gemma-4-12b-it` 載入的 context 是 8192。實戰題目第一次嘗試就有 26% 爆 context（HTTP 400「Context size has been exceeded」），評估集是 12%。這段照規定沒有碰伺服器。如果要讓 12B 上線，建議由使用者把載入的 context 調大（例如 16384），或另開一段縮小提議 prompt 和 schema。這是今天退回率的最大來源。
2. **出題檢查的 CPU 成本**：每張白板平均多 4.3 秒，最大 24 秒，主要花在不可行的核心反覆檢查。可以考慮兩種做法：
   - 把 `WITNESS_MAX` 從 48 降到 24：可行題的檢出率從 93% 降到 86%（以 400 份為基準），耗時約減半。
   - 改成「每次出題總共最多驗證 N 份」。
   原型值目前沒有改。
3. **出題多樣性下降**：265 題的不同核心原語從 43 種降到 27 種。不可行的大多是揭露、驅散、淨地、地形、持續區域這類沒有數值或版型特殊的核心。另外，`make_topic` 回傳 `None`（這一格不請 LLM）的比例從 1／114 升到 30／275。請決定這個取捨能不能接受。另一個做法是只對兩個關鍵字的題目套用檢查。
