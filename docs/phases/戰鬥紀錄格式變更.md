# 戰鬥紀錄格式變更

> 戰鬥紀錄（`BattleLog`，`trpg battle --log-json` 與網頁 API 的 `/log` 輸出）的版號 `LOG_FORMAT`（`src/trpg/engine/runner.py`）之策略與變更歷程。2026-10-29（Phase 3T-2）由 `runner.py` 的 docstring 搬來；舊條目一字未改。

## 1. 策略（Phase 3T-2 起）

戰鬥紀錄記的是 `setup（含內嵌的規則包）＋ seed ＋ 步驟列表`，重播就是用同一個引擎把步驟再跑一遍。要能重播，必須同時符合兩件事，兩件事分開處理：

| 問題 | 由誰回答 | 怎麼檢查 |
|---|---|---|
| 紀錄的 **結構與結算語意** 引擎還懂不懂？ | `format`（`trpg-battle-log/N`） | `format != LOG_FORMAT` 就拒絕重播，並說明舊格式無法重播 |
| 紀錄裡的 **規則包內容** 有沒有被改過、或資料結構變了？ | `ruleset_hash` | 重播前對內嵌的 `setup.ruleset` 重新計算 SHA-256，和紀錄的 `ruleset_hash` 比對，不符就給中文錯誤 |

### 1.1 什麼時候要遞增版號

只有 **紀錄結構或結算語意改變** 才遞增 `LOG_FORMAT`：

- 事件、動作、決定、戰鬥狀態、`BattleLog` 的欄位增減或型別改變；
- 同樣的規則包與步驟，新引擎算出的結果和舊引擎不同（結算規則、事件順序、亂數取用次數改變）。

### 1.2 什麼時候 **不** 遞增

- 新增或修改內容檔（技能、種族、地圖、數值……）：規則包內嵌在紀錄裡，重播不讀內容資料夾，內容不同的紀錄由 `ruleset_hash` 區分。Phase 4 起 LLM 生成技能之後，每一局的規則包都可以不同，這是正常情況，不再靠升版號表達。
- 規則包的 **資料結構**（`Ruleset` 的欄位、`content/*.yaml` 的 schema）增減：新增有預設值、不影響舊內容結算的欄位，不升版號；但舊紀錄內嵌的規則包重新載入後序列化結果會和紀錄時不同，`ruleset_hash` 比對不符 → 舊紀錄會被拒絕並說明原因。若要保留舊紀錄可重播，必須另外提供遷移，不在目前範圍。
- 只改文字、說明、介面。

### 1.3 改版時的流程

1. 在本文件第 2 節最上面加一條 `` `/N` ``（Phase 與一句話原因、舊版是否仍可重播）。
2. `runner.py` 只更新 `LOG_FORMAT` 與其 docstring 的一行說明。
3. 用 `git grep "battle-log/<舊版>"` 找出測試中的字面值一併更新。
4. CLI 快照有變時說明原因再用 `UPDATE_CLI_SNAPSHOTS=1` 重產。

### 1.4 `ruleset_hash` 的算法

`trpg.engine.ruleset_hash.hash_ruleset(ruleset)`：`Ruleset.model_dump(mode="json")` → 排序鍵、無多餘空白、不跳脫中文的 JSON → SHA-256 十六進位。不使用內建 `hash()`。這和 roguelite 存檔的 `ruleset_hash(library)`（內容資料夾全部檔案的雜湊，判斷「存檔建立後內容資料夾有沒有改」）是兩個不同的東西：前者看紀錄內嵌的規則包，後者看磁碟上的內容庫。

### 1.5 重播時的檢查順序

`trpg.engine.runner.log_replay_problem(log)`（`trpg replay` 使用）：

1. `format` 與目前不同 → 「不支援的紀錄格式…舊格式的紀錄無法重播」；
2. 缺 `ruleset_hash` → 「紀錄缺少 ruleset_hash」；
3. 內嵌規則包的雜湊與 `ruleset_hash` 不符 → 「紀錄的規則包雜湊不符」；
4. 通過後才重播，並比對最終狀態與事件。
