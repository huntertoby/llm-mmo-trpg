## 部署時一定要注意的兩件事

1. **Gemma 在 LM Studio 不吃 `chat_template_kwargs`**，每次都先「思考」約 800 token；`max_tokens` 1024 時常常整個被思考用光，回傳空字串。請求帶 `reasoning_effort: "none"` 才不思考。正式用 Gemma 時 `config/llm.toml` 要設 `reasoning_effort = "none"`。
2. **LM Studio 把 context 分給同時進行的請求**：4 個平行時一直回「Context size has been exceeded」（我們的 client 會把這個 400 誤報成「拒絕了所有 JSON schema 寫法」）。5E-4 的「LLM 單一佇列、同時 1 個」是必要的。

## 情境判定（新評估，沒有 27B 對照）

雲嶺 30 個模板（荒原還沒有情境模板），每個用三種回答各問一次，共 90 題。

| 指標 | 結果 |
|---|---:|
| JSON 合格／一次通過 | 90/90（100%），沒有退回 |
| 好答案 → `dc_shift ≤ 0`、沒有劣勢 | 30/30（−2 有 20 題、−1 有 9 題、0 有 1 題） |
| 亂答 → 劣勢或 `dc_shift ≥ 1` | 30/30（28 題同時給劣勢與 +2） |
| 注入（要求 −10、999 經驗） | 30/30 沒有給負的 `dc_shift`；但 **13/30 勾了用心清單**（注入文字其實沒用到任何事實） |

注入的結果：獎勵與數值都守住了，schema 與引擎的範圍檢查擋得住。但「用心清單」被誤勾的比例偏高。要不要在引擎端加一道「勾選的事實要在玩家文字裡找得到關鍵詞」的檢查，列為待決。

## 說書人（新評估，沒有 27B 對照）

- 事件開場 21 個：20 個用 LLM，1 個退回模板。
- NPC 聊天 16 次（一般問題 8、注入 8）：16/16 用 LLM、沒有退回；注入時 NPC 照角色回應，沒有照做。
- 抽樣的文筆通順，有符合場景與人設。少數用詞偏書面，例如「焦煿」。

## 結論與建議

- **情境判定、說書人、閃現：Gemma 夠用**。品質與 27B 相近或沒有明顯問題。
- **完整技能提議：Gemma 明顯比較差**。升級候選退回多了 14 個百分點，強制測試多了 24 個百分點。但退回後有組合器補位，玩家不會卡住，只是 AI 長出來的技能比例變少（升級候選約一半）。
- 建議：
  1. 部署在 Mac mini 時，大世界的情境判定與說書人用 Gemma。
  2. 技能提議接受較高的退回率，或者這一項之後改用雲端或較大的模型；`config/llm.toml` 可以為技能另設端點，屬於後期項目。
  3. 如果要讓 Gemma 的技能提議接近 27B，可以排一段「針對 Gemma 調提示與 schema」，參考 4-L10 的做法，先從 `value_error` 與 `budget.weak` 下手。
- 待決（給使用者／專案 PM）：
  - 正式要不要改用 Gemma（`config/llm.toml` 的 `base_url`、`model`、`reasoning_effort`）。
  - 技能提議退回率較高能不能接受。
  - 情境判定的「用心清單」要不要加引擎端檢查。
