# Phase GS-3 計畫：化身進入效果、護盾看最大 HP、天生武器屬性、實心環形（#173）

> 來源：`docs/玩法決定紀錄.md` #173（a5f839192）。使用者原話：「改規則再補（建議）」、「一起改成原設計（建議）」。規格在 `docs/design/06-技能.md` 6.30「形態池名單」最後一點，以及第 29 行的形狀清單。另見 GS-2 報告與開發 PM 裁定。
> 排在 HC-6a 之後；兩段都可能改到 content schema 和工坊白名單。

## 受影響的既有功能（開工先盤點，寫進報告）

引擎結算（形態進入、護盾、縮放屬性、目標形狀）、content schema 與驗證、技能預算計價、技能卡和說明文字、工坊白名單、組合器（會不會用到新參數）、LLM 提議的 schema、前端技能卡與範圍預覽、存檔與戰鬥紀錄（`LOG_FORMAT`）、快照。

## 範圍

1. **`enter_form` 可以帶 1 個進入時效果**：
   - `enter_form` 不再要求是唯一效果，改成必須是第一個效果；後面最多再跟 1 個，只能是 `apply_status` 或 `push`。只有 3 階以上可以帶。
   - 進入時效果的形狀只能是自己，或「周圍 1～2 格」（第 4 項的實心環形）。
   - 結算順序：檢查能否變身 → 付 AP → 變身 → 形態的進入獎勵 → 進入時效果。
   - 化形專精的 ×1.5 和形態幅度都**不**乘在進入時效果上。
   - 預算：形態技能的算法，再加這個效果的點數（照形狀倍率）。合格範圍照樣是 70～100%。
   - 帶進入時效果的化身技要有冷卻，至少 2，初值 3。這個下限放進 content 規則，並開進工坊。
2. **`shield` 新增「最大 HP ‰」參數**：每個目標得到的護盾 ＝ 施放者目前（變身後）的最大 HP × 這個‰，不加屬性。
   - 預算點數的初值照「化形守護維持 GS-2 的比例（約 77%）」反推，寫進 `skill_budget.yaml` 並開進工坊。
   - 量類換算（×10）照 `scripts/x10/fields.yaml` 判斷並登記。
3. **縮放屬性新增「天生武器」選項**：只有條件是「在形態中」的技能可以用。
   - 命中和傷害都用目前形態天生武器的屬性。天生武器有兩個屬性時，照 08 8.11 取較高的那個。傷害元素照舊。
4. **`ring` 新增「實心」參數**：「周圍 N 格」＝ 切比雪夫距離 1～N，不含自己。
   - 預算的形狀倍率要照涵蓋的格數。照 HC-B 的做法進 `shape_budget`，並開進工坊。
   - 範圍預覽（前端）要畫對。
5. **改 4 招、補 4 招**（內容照 06 6.30）：
   - 化形守護：改成護盾 ＝ 最大 HP × 150‰，持續 2 回合。
   - 野性連擊：改用天生武器屬性。
   - 化形震地、原形歸一：改成實心環形 2。
   - 補 4 招高階化身：熊王怒吼（3 階史詩）、影貓潛襲（3 階稀有）、巨人踐地（4 階稀有）、龍威降臨（4 階史詩）。都是姿態、法術類別、不限武器，帶進入時效果，冷卻 3。
   - 每招都要有 `narrative`（`concept`、`cast_flavor`，繁中）。不當起始技能。
   - 預算照樣是 70～100%，取最保守的初值。
6. **新參數都開進工坊**：每格要有中文名，並寫清楚調高、調低的效果。

## 不做

- 不跑模擬。150‰、冷卻 3 都是初值，由使用者在工坊調。
- 不讓組合器或 LLM 主動用新參數，只要 schema 能接受、驗證會擋就好。要讓組合器會用，另外排一段。
- 不改 `docs/design/`。

## 驗收

- **行為一致測試（實際跑引擎）**：
  - 進入時效果的結算順序，以及不乘專精和形態幅度。
  - 2 階帶進入時效果會被擋下。
  - 實心環形 1～2 格涵蓋貼身的敵人，不含自己。
  - 護盾 ＝ 變身後最大 HP × ‰。
  - 天生武器屬性：用於命中與傷害；雙屬性時取較高。
  - 冷卻下限會擋下冷卻太短的化身技。
- **靜態檢查**：`trpg content check` 通過，8 招都在 70～100%。報告附每招的比例。
- **不受影響的部分**：
  - 原有招（438 招減掉改的 4 招）逐招預算 different=0。
  - 78 場戰鬥 different=0。有差異的話，只能來自改的 4 招，要寫原因。
  - 組合器 recipe census 小樣本 different=0。
- **`LOG_FORMAT`**：照 `docs/phases/戰鬥紀錄格式變更.md` 判斷要不要升。新參數有預設、舊紀錄結算不變的話不升；要升就照 1.3 的流程。
- **API 與前端**：API 有改就重產 OpenAPI。前端有改，tsc、vitest、build 都要過。
- **靜態工具**：ruff、format、mypy、lint-imports、`classify.py --check` 都要 0。
- **測試**：
  - 開發中經看門狗只跑相關的測試。
  - **交件前全部 commit 之後，先問開發 PM「能不能跑」**。照 PM 回覆做：可能要先 `git merge --no-edit main`，再跑 `uv run python scripts/check.py` 和 slow 的 parity、cli。有失敗就修、commit、重跑，直到全過。
- **快照**：照常重產。先預測、再逐鍵核對。CLI 用 `-n 0`。parity 照 GS-2 的做法只補改到的招。
- **commit 與報告**：每項一個 commit，報告寫在 `docs/phases/PhaseGS-3報告.md`。
