# LLM 品質評估：Gemma 12B、27B、Gemma 31B 同 commit 比較（2026-11-04）

只比品質（正確率、JSON 合格率、退回率），**不量速度**（使用者：「等等測試只能測試聰明程度喔 因為現在是在windows 實際上 mac的 速度 能不能跑是一回事」）。耗時數字只是 Windows 上的參考，不代表 Mac mini。

- 程式碼：三個模型都在 commit `6af12836`（src、content、scripts、tests 相同），題目、種子、重試次數相同。31B 在 `6af12836` 的唯讀 worktree 上跑，因為那時 main 已經往前了。
- 端點：LM Studio `http://127.0.0.1:1234/v1`，用環境變數指定，`config/llm.toml` 沒改。
  - Gemma 12B：`gemma-4-12b-it`。
  - 27B：`swift-1.5-qwen3.8-27b-uncensored-dynamic-mtp`（使用者：「swift 開好了」）。
  - Gemma 31B：`gemma-4-31b-it`（使用者：「llm gemma-4-31b-it 我開這我沒跟你講嗎?」）。31B 就算用 Q4 也要 18GB 以上，Mac mini 16GB 放不下，所以這組只看品質上限，或評估留在 Windows 上跑的方案。
- 設定：三個都 `TRPG_LLM_REASONING_EFFORT=none`（27B、31B 都試打確認思考 token 為 0），一次一個請求（`--workers 1`）。

### Gemma 31B 的細節

- 技能：升級候選明顯最好，退回 34%，另外兩個約 50%。主要錯誤和 27B 同類：`budget.weak` 26 次、`keyword.required` 13 次。自由測試一次通過只有 49%，比 27B 低，但重試後累計 98.3% 最高，也就是第一次常差一點、看了錯誤訊息改得回來。
- 閃現：介於兩者之間。主要錯誤是 `flash.duplicate`、`flash.note_zh.world_terms`（各 20 次）與 `flash.note_zh.missing_added`。
- 情境判定：好答案多給 −1（33 題），−2 有 7 題、0 有 6 題；亂答 45 題給 +2 加劣勢。注入 46 題都沒勾用心清單，沒有給負的 `dc_shift`。
- 說書人：文筆接近 Gemma 12B，會寫 `more_zh` 補充段；抽樣沒看到講錯人。

## 細節（Gemma 12B 與 27B）

### 技能提議

- 兩邊 HTTP 全 200、結束原因全 `stop`，沒有 JSON 錯誤。
- **升級候選兩邊都約一半退回**，差距只有 4 個百分點。主因是兩邊共通的引擎修補與驗證：`budget.weak`、`exclusion.no_cooldown_big_area`。這表示升級候選的退回主要在題目與驗證器本身，換大模型幫助不大。
- 錯誤種類不同：
  - Gemma 最多的是 `value_error`（選填欄位組合，32 次）。
  - 27B 最多的是 `budget.weak`（47 次）與 `keyword.required`（23 次）。27B 格式守得好，但數值偏保守。
- **強制測試與自由測試 27B 明顯好**，退回少約 24 和 5 個百分點。

### 閃現變化

- 退回模板一樣是 8%，玩家都拿得到東西。
- 27B 的「模型湊滿」反而比較少：`flash.note_zh.missing_added` 有 28 次，Gemma 只有 11 次，也就是敘述裡漏寫新增的效果。名稱與敘述較短、較直白。

### 情境判定

- 兩邊都全部一次合格。
- **好答案的給分**：Gemma 多給 −2（25 題），27B 幾乎都給 −1（45 題）。兩種都在規則範圍內，27B 比較保守。
- **注入**：
  - 兩邊都沒有給負的 `dc_shift`。
  - 27B 46 題全部沒勾用心清單；Gemma 有 1 題勾了，但引擎端的檢查已擋下。
  - 27B 對注入比較兇：27 題直接給 +2 加劣勢。

### 說書人

- 兩邊都全部用 LLM。
- 文筆差異：
  - Gemma 的開場較長，會寫 `more_zh` 補充段。
  - 27B 較短、較冷硬，`more_zh` 幾乎都留空。
- 抽樣看到 27B 一個小問題：問灰鬚（greybeard）時，回答用了老鐵的口頭禪「嘿」，`npcs` 也填成老鐵，等於換了一個人講話。Gemma 的抽樣沒有這個問題。
- 注入的聊天兩邊都照角色回絕，沒有照做。

## 結論與建議

- **情境判定、說書人**：三個都夠用，差別在文筆。27B 偶爾會講錯人。
- **閃現**：Gemma 12B 最好，31B 次之，27B 最差；三個退回模板的比例都一樣是 8%。
- **技能提議**：
  - 升級候選：31B 最好（退回 34%）。另外兩個約一半退回，問題主要不在模型。
  - 強制測試：27B 與 31B 差不多，都明顯比 12B 好。
- **建議**：
  1. 部署在 Mac mini、只能放一個 16GB 以內的模型時，用 **Gemma 12B 就可以上線**。大世界文字都沒問題，技能退回後有組合器補位，不會卡住玩家。
  2. 31B 品質最好，但放不進 Mac mini 16GB。只有「模型留在 Windows 跑」的方案才用得上。
  3. 升級候選的退回率另外由 6S-2（提示與確定性補強）處理，改善後的數字見下節。
- **待決**（給使用者／專案 PM）：
  - 正式用哪個模型：`config/llm.toml` 的 `base_url`、`model`，以及 `reasoning_effort = "none"`。
  - 模型放在 Mac mini 還是留在 Windows。

## 6S-2 改善前後（Gemma 31B，2026-11-04）

6S-2 動了兩處：升級候選的提示詞，以及確定性的補強修補。驗證規則和預算都沒有放寬。前後用同一個模型（`gemma-4-31b-it`），所以可以直接比。

- 改善前：commit `6af12836`（上表 31B 那一欄）。
- 改善後：commit `967643c8`，含 6S-2，不含 6S-2b。6S-2b 只補 LLM 失敗後的保底，不影響模型表現。設定照舊：`reasoning_effort=none`，一次只送一個請求。
- 注意：6S-2 改了出題，帶不到關鍵字的組合會換核心或換稀有度。所以升級候選裡有關鍵字的題目，和改善前不完全是同一批；沒有關鍵字的題目完全相同。

### 技能多樣性（只看 LLM 合格的技能）

統計腳本在開發 PM 的暫存資料夾（`diversity.py`），讀每次評估的 `skills.csv`，分組依據是 `chosen_primitives`。

| run | LLM 合格 | 靠 topup 才合格 | 不同效果組合 | 最常見組合（占比） | 含 damage 占比 |
|---|---:|---:|---:|---|---:|
| 12B 改善前 | 375 | 0 | 66 | 施加狀態＋傷害（60.0%） | 79.2% |
| 12B 6S-2 | 388 | 1 | 74 | 施加狀態＋傷害（45.9%） | 80.9% |
| 12B 6S-2c | 402 | 4 | 75 | 施加狀態＋傷害（41.0%） | 78.6% |
| 31B 改善前 | 435 | 0 | 65 | 施加狀態＋傷害（40.7%） | 75.9% |
| 31B 6S-2 | 441 | 1 | 78 | 施加狀態＋傷害（31.5%） | 79.6% |

- **補強沒有造成集中**：靠 `topup` 才合格的技能每輪只有 0～4 招。6S-2 之後，不同組合變多、最常見組合的占比下降，12B 從 60% 降到 41%。
- **集中是模型本身的傾向**：「施加狀態＋傷害」一直最多，含傷害的占比都在八成左右。這和補強無關，要再分散，得從提示的出題方向下手。
- **6S-2c 的改動**：附帶效果改成依骨架偏好、再依種子輪替；新增「對敵方施加有害狀態」這種附帶效果。Mock 的分布從 damage 5／heal 4 變成 damage 2／shield 4／狀態 3（報告見 `Phase6S-2c報告.md`）。
