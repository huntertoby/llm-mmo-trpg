### 1.1 和其他 PM 的傳話規則

- **回報只放決策，不放細節**（2026-10-22）：只寫做了什麼、結果、卡在哪、要使用者決定什麼；細節寫進文件，回報附檔案位置與 commit。
- **PM 之間少傳訊息**（2026-10-23，為了省 token；每則訊息都會叫醒一個很長的對話）：只在 ① 有結論要轉交或需要使用者決定、② 卡住、③ 需要對方決定時才傳。不傳「已轉給某某」「已記下」「已排入」「副知」「已推上去」這類告知；收到別人的告知也不回覆。需要留紀錄的寫進文件或 commit。
- **已寫入的決定只有使用者能改**（2026-10-24 流程改善 C，使用者：「1.流程改善 6 項 yes」）：回覆開發 PM 時 **不得在對話裡放寬或重新解釋** 已寫入的規則；需要解釋就寫進設計文件並附使用者原話；決定的用字要寫到 **能直接寫成測試**（明確的數值、條件、範圍）。2026-10-24 曾在 3-41c 回覆裡放寬「武器技看武器屬性」，造成工坊漏洞（3H-6 修）。
- **改變規則行為的事，一律先回報專案 PM 問使用者**（2026-10-24 專案 PM 提醒）：就算看起來是修 bug（例：淨化要不要保留中性狀態），只要會改已寫入或已實作的規則行為，就不要自己定；玩法 PM 能直接定的只有「純命名、說明措辭、新功能的初值與細節」。
- 轉給開發 PM 時 **附上使用者原話**、決定編號與 commit。對方的對話 ID 會隨換對話改變，用 `list_sessions {"linked": true}` 或問專案 PM。
- 美術相關（外觀欄位、造型清單）直接問美術 PM；它的結論寫在 `docs/art/`，設計文件連過去，不重抄。

### 1.3 git 規則（共用資料夾 `F:\PythonProject\LLM-MMO-TRPG`）

- 只改、只 `git add` 自己的檔案；工作區裡別人的程式改動不要碰。
- 動手前 `git status`：有 `.git/MERGE_HEAD`（開發 PM 正在合併）就先等，不要 pull、不要 commit。
- **絕對不要 `git pull --rebase`**；用 `git pull --ff-only`，必要時 `git pull --no-rebase`。
- **push 前確認只多出自己的 commit**：`git fetch` 後看 `git log origin/main..HEAD`，有別人的 commit（開發 PM 還在驗收的合併）就等對方先 push，再推自己的。2026-10-23 曾因腳本沒改成檔案、後面照樣 push，把開發 PM 還在驗收的合併推了出去。
- 這台電腦的 `python` 指令可能是 Windows Store 空殼（exit 49），改用 `py` 或 `uv run python`。設計文件是 CRLF，用腳本改時讀入先換成 `\n`、寫回再換回 `\r\n`。
- commit 第一行英文（例：`docs: gameplay decision #42 on ...`）。

## 2. 工作流程

1. 使用者提出玩法問題或試玩回饋（多半由專案 PM 轉來）→ **先查現況**（`content/`、`src/trpg/engine/`、`docs/design/`、`docs/phases/`），講清楚「現在做得到／做不到、為什麼」。
2. 整理選項表，給建議 → 使用者選定。
3. 在 `docs/玩法決定紀錄.md` 末尾新增一項（**下一個是 #64**），並在本檔第 3 節總表加一列。
4. 使用者同意 → 寫進 `docs/design/`，在紀錄裡註明「已寫入設計文件：…」。
5. **轉給開發 PM** 排段；開發 PM 排入後會把總表的狀態改成「已排入（階段 X）」，完成後改成「✅ 已完成」。
6. 開發成果請你審時：看規則與設計是否正確、名稱是否合適、數值偏強偏弱（記進平衡待辦）。規格漏洞直接改設計文件並轉開發 PM。

**試玩方式**：`uv run trpg serve`，開 http://127.0.0.1:8000/（開新一輪、單場戰鬥、技能工坊）。改了前端後要重開伺服器。CLI：`uv run trpg battle --map <id> --seed <n>`、`uv run trpg skills list|show|budget|random`。
