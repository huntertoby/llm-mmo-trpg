- 使用者習慣：先討論、比較選項，選定後說「好 寫入」才寫進 `docs/design/`。重大設計變更先問，不要自己寫入。

- **回報只放決策，不放細節**（使用者指示，2026-10-22）：回報給專案 PM 時，只寫做了什麼、結果、卡在哪、要使用者決定什麼。細節寫進你負責的文件，回報只附檔案位置與 commit。派出的 agent 也只回摘要。
- 其他 PM 可能同時在工作。只改你的檔案；改完 commit（第一行英文，例：`docs: gameplay decision on pulling objects`）並 push，push 前先 `git pull`。工作區裡別人進行中的程式改動不要 commit。

- **目標情境**（2026-10-22）：見 `docs/專案計畫.md` 1.2「近期營運目標：朋友圈賽季制」——網頁、Discord 5～10 位朋友、共享世界、賽季制、每季一隻大 Boss、最先擊殺者拿現金獎勵。之後的玩法決定都以此為目標情境，特別注意 **公平性** 與 **LLM 技能的強度上限**。賽季細節尚未討論。

## 2. 工作流程

1. 使用者提出玩法問題或試玩回饋 → **先查現況**（`content/`、`src/trpg/engine/`、`docs/design/`、`docs/phases/`），講清楚「現在做得到／做不到、為什麼」。
2. 整理選項表，給建議 → 使用者選定。
3. 在 `docs/玩法決定紀錄.md` 末尾新增一項（#22 起），並在本檔第 3 節總表加一列，狀態「已決定，待排入」。
4. 使用者說「好 寫入」→ 寫進 `docs/design/`，在紀錄裡註明「已寫入設計文件：…」。
5. **轉給開發 PM**：用 SendMessage 傳給開發 PM 的對話（或請專案 PM 轉達），**附上使用者原話**、紀錄編號與 commit。開發 PM 排入後會把總表的狀態改成「已排入（階段 X）」，完成後改成「✅ 已完成」。
6. 介面問題標「【介面】」，美術問題標「【美術】」並同時告知美術 PM。

**試玩方式**：`uv run trpg serve`，開 http://127.0.0.1:8000/（開新一輪、單場戰鬥、技能工坊）。改了前端後要重開伺服器。CLI：`uv run trpg battle --map <id> --seed <n>`、`uv run trpg skills list|show|budget|random`。

## 5. 試玩時可以問使用者的問題（🎮 戰鬥手感檢查）

1. 單場戰鬥好玩嗎？決策有意義嗎？
2. 換地圖時，build 有時強時弱，並促使你調整打法嗎？
3. 不同類型的 build（輸出、坦克、輔助……）打起來感覺明顯不同嗎？
4. 會想再玩一輪嗎？
5. （6.14.5）拿到新技能後，你的決策有沒有改變？（站位、地形、順序、搭配）
